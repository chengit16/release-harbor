## 2026-11-04 确定的优先级

1. 保留华为 AppGallery 的 Android 草稿能力。
2. Android 新渠道依次为：**小米 → OPPO → vivo → 魅族 → 荣耀**，每次只开发和验证一家。
3. 上述 Android 渠道完成后恢复 **iOS／Apple**，未完成的 Apple 改动继续隔离保留，不作为当前 Android 开发的阻塞。
4. **应用宝、华为鸿蒙**放到上述 Android 与 iOS 渠道完成后另行安排，二者内部顺序届时确定。已有华为 Android 草稿不等于华为鸿蒙支持。

Apple 延后是开发顺序调整，不表示第一期原始验收范围已经全部完成。SDK 导出能力不等于当前产品已支持。

## 发布操作简化

开发接入阶段需要核实每家平台的差异；日常发版不要求用户重复研究或手工跑完技术步骤。

华为、小米、OPPO、vivo、魅族和荣耀 已实现交互：选择渠道与安装包、填写资料 → 点击“准备发布” → 系统自动只读校验并准备快照 → 在摘要中明确确认一次 → 系统执行并展示回执。

只读预检、快照与一次性授权仍由系统落实，界面不再要求用户依次切换预检、冻结、确认、执行四个入口。账号配置一次后复用；材料或目标变化时才提示处理。不同商店沿用同一操作方式，但最终确认明确显示真实动作，例如“小米提交审核”与“华为保存草稿”。

P2-0 公共入口已在华为链路完成工程实现与隔离浏览器验证；本轮未重新运行真实商店上传。小米切片也已完成工程及隔离浏览器验证，使用指南见[小米更新](guides/xiaomi-updates.md)。用户已反馈小米可用并授权 OPPO；OPPO 已完成工程接入、真实待验收，不同时展开后续渠道。

## 排期与验收

执行顺序为实施计划 → 切片规格 → 实现 → 工程验证 → 具体渠道真实验收。单渠道交付后才推进下一家；材料缺失时标记待验收，调整顺序按用户后续指令执行。批次与并发在单渠道流程稳定后按需落地，不提前构建通用任务平台。

在线接口从第一期预留，但身份与授权未落地前不直接公网暴露本地 API。不承诺材料缺口尚未明确时的固定工期；平台处理等待与工程工时分开记录。

OPPO 普通应用单 APK 更新已完成工程接入，沿用自动准备与一次确认，支持立即／定时意图及异步任务结果核对；真实 OPPO 验收待用户在具体计划执行。小米已获用户可用反馈，vivo 本轮工程接入、真实待验收，魅族与荣耀已工程接入、真实待验收，Apple 继续暂缓。

## 2026-11-06 官方状态查询与本地发布解耦

用户明确更正：审核状态应直接查商店，不以本地发布记录为前提。此安排取代前述仅已执行记录及锚点限定的主入口；旧按计划观察仍在“本地发布关联”保留，不能混淆目录版本与原执行关联。

默认“商店状态”列出当前应用的所有绑定，官网手动提交版本亦可查询。魅族读取官方 `/app/versions` 目录（没有构建号）；荣耀分开当前审核流程与已上架版本；Apple 读取版本及构建目录。vivo 只映射已核实待审核状态；OPPO、应用宝、鸿蒙读取官方版本资料，未核实审核字典时保持未知。小米说明官方未开放；华为 Android 说明独立查询尚待核实接入。具体范围见[查询指南](guides/release-status-observations.md)。第三期资料待办仍在后续范围，不能据此标记第三期完成。

新 GET `/api/store-status` 仅读取可信绑定目录与缓存；POST `/api/store-status/:projectId/:applicationId/:bindingId/query` 要求本机来源及固定标记、空正文，从目录恢复目标进入独立 worker。API 不加载 SDK 或凭据。新 `store-status.json` 以绑定指纹隔离预约和快照，单进程队列原子写入；未完成预约三分钟、已完成十秒内避免重复，不自动重试。失败保留上次成功及其时间，导航不请求商店，不改写任何计划、回执、授权及人工核对。真实查询由用户具体目标另行验收。
