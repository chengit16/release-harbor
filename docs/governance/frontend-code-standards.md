# Web 前端代码规范

**修订日期：**2026-11-03  
**适用范围：**`apps/web` 及其相关测试；`packages/contracts` 的公开类型注释同时遵循后端规范。  
**执行要求：**本规范是人工与 AI 开发、重构、修复和评审的必读约束，从本次建立后对新增及实际修改的代码生效。历史代码按修改范围渐进调整，不借任务批量重写无关内容。

本规范参考 KnowSpace 的 `frontend-code-standards.md`，结合本项目的 [协作约定](../../AGENTS.md)、[领域术语](../../CONTEXT.md)和[架构设计](../ARCHITECTURE.md)制定。以下规则在本仓库内完整生效，不要求开发者访问 KnowSpace。

## 1. 技术基线与职责边界

- 使用 React、TypeScript、Vite 和现有 CSS。使用 pnpm，依赖版本固定并同步 `pnpm-lock.yaml`。
- 当前没有采用 React Router、TanStack Query、Zustand、Ant Design 或 UnoCSS。出现真实需要时再评估引入，不因参考规范自动增加依赖。
- Web 通过 `@release-harbor/contracts` 使用公开合同，不导入 `apps/api`、`@release-harbor/domain`、NestJS、Node 文件系统、`@release-harbor/provider-app-ship` 或商店 SDK；领域校验的权威实现留在服务端。
- 当前只提供项目创建、读取、本机持久化与规划展示。未完成能力必须标明“待实现”或“待接入”，不能生成模拟发布成功、审核结果或上线状态。
- 前端权限属性、按钮禁用和输入校验用于交互提示，不能替代服务端授权及校验。

## 2. 目录、命名与规模

现有入口为 `src/main.tsx`、`src/App.tsx` 和 `src/style.css`。新增能力按真实职责逐步拆分，以下是目标组织方式，不要求预建空目录或一次迁移现有代码。

```text
apps/web/src/
  app/                       应用壳层、Provider 与错误恢复
  routes/                    引入路由后维护页面定位
  pages/{domain}/{feature}/  页面入口、业务 Hook、配置与私有组件
  components/                跨页面复用的展示与交互组件
  api/client.ts              统一 HTTP、错误解析与取消处理
  api/services/{domain}/     按领域组织的接口能力
  hooks/                     跨页面 Hook
  store/                     确有跨页面需求的客户端状态
  styles/                    设计变量与公共样式
  utils/                     无 React 和 Store 依赖的纯函数
```

页面不创建独立 HTTP Client；公共组件不依赖具体页面；API Service 不处理弹窗、导航和页面状态；Store 不复制 URL、请求结果和表单状态。类型以公开合同或最近使用方为归属，不建立包罗所有内容的 `types.ts`、`utils.ts`。

组件文件和组件、类型使用 `PascalCase`；业务目录、Service 文件和普通函数使用 `camelCase`；页面入口可使用 `index.tsx`。Hook 使用 `useXxx`，布尔值使用 `is/has/can/should` 前缀，事件处理函数使用 `handleXxx`，回调属性使用 `onXxx`。公开合同沿用现有 `CreateProject`、`ApiError` 等命名和 `workspaceId` 等字段，不因本规范机械改名。

| 文件类型               | 推荐范围 |    预警范围 | 处理方式                            |
| ---------------------- | -------: | ----------: | ----------------------------------- |
| 页面入口               |  ≤150 行 | 151～250 行 | 抽取业务 Hook、配置或独立交互组件。 |
| 页面私有组件           |  ≤200 行 | 201～350 行 | 按独立交互拆分。                    |
| 公共组件               |  ≤300 行 | 301～500 行 | 保持公开接口，拆内部职责。          |
| 业务 Hook、Store、工具 |  ≤300 行 | 301～500 行 | 按状态所有权或业务能力拆分。        |

行数只是职责预警，配置、生成文件和大段声明式数据另行判断。超过预警上限时先评估职责；确需保留应说明原因，不继续堆叠新职责，也不以无意义转发函数规避。

## 3. TypeScript、组件与状态

- 保持现有 `strict` 和 `noUncheckedIndexedAccess`。外部未知值使用 `unknown` 并验证，类型断言不能替代运行时检查；禁止用 `any`、双重断言或非空断言掩盖缺失状态。类型导入使用 `import type`，有限状态优先使用字面量联合。
- 使用函数组件与 Hook，公共组件优先具名导出；一个文件维护一个主要组件。列表使用稳定业务 ID 作为 `key`。
- 渲染保持纯净，不在渲染时发请求、写存储或触发业务动作。不用 Effect 复制可以由 Props、输入或请求结果直接推导的值。
- Effect 用于与外部系统同步，并清理请求、订阅、计时器；旧响应不能覆盖新的项目详情，卸载后的异步结果不能继续更新页面。
- Props 表达组件所需的最小数据和回调；不要向纯展示组件透传完整业务实体。修改公共组件时同步检查调用方、回调参数与触发时机。
- `useMemo`、`useCallback`、`memo` 仅用于已确认的计算成本或稳定引用要求；业务 Hook 优先返回具名对象。

| 状态                     | 当前归属                     | 约束                                                     |
| ------------------------ | ---------------------------- | -------------------------------------------------------- |
| 项目列表、详情、能力信息 | 页面业务 Hook，通过 API 获取 | 服务端结果是事实来源；变更后重新读取或精确更新相关数据。 |
| 表单草稿、校验、弹窗     | 组件或局部 Hook              | 请求失败保留输入，刷新数据不覆盖未保存草稿。             |
| 可分享的页面定位与筛选   | 需要深链时放入 URL           | 不把 URL 参数当作身份或授权。                            |
| 跨页面客户端短期状态     | 确有需要时提取 Store         | 不复制其他层已经维护的状态，不持久化秘密。               |

后续若引入查询缓存，查询键必须覆盖可信工作空间、资源 ID、筛选和分页等影响结果的条件。实现工作空间或账号切换时，隔离旧请求、订阅、缓存和草稿；不得把旧响应写入新上下文。当前固定 `local` 不代表已具备多租户能力。

## 4. API 与发布交互

- 新增或实际修改请求逻辑时，统一收敛到 `api/client.ts` 与领域 Service，页面、组件和 Store 不新增直接 `fetch`。迁移请求时同步迁移受影响调用方，不复制第二套 Client。
- Client 统一处理同源基址、HTTP 状态、JSON 解析、取消及网络错误。非 2xx 响应不能按成功处理；公开响应先做与实际字段相符的运行时检查，不能只写 `as Project`。
- 当前错误合同为 `{ statusCode, message }`，不假定已存在错误码、Trace ID、认证会话或幂等键。新增这些能力时先更新合同，再同步服务端、调用方和测试。
- 每个异步交互提供加载、空数据、成功和失败状态；已实现对应接口时，再明确无权限、冲突和结果不明等状态。提交中防止重复触发，成功状态以服务端返回为准。
- 创建失败保留表单；冲突时展示原因，不静默覆盖。后续送审、上线等动作必须核对确定的计划、目标、动作与授权范围；不能因页面刷新或重连再次触发。
- 规划、执行事实、商店回执和远端状态观察分别展示。上传成功不等于送审成功或已上架；断网不等于撤回成功。
- 浏览器选择的文件不等于云服务器可读取的路径。后续产物交接必须使用明确上传或受信任执行器合同，不将本机绝对路径作为公开 API 参数。

## 5. 样式、可访问性与安全

- 遵循现有 `.prettierrc.json`：单引号、无分号、尾逗号、100 列；缩进使用 Prettier 默认的 2 空格。不要复制参考项目的双引号与分号风格。
- 导入按第三方、工作空间包、相对路径、样式资源组织，初始化所需副作用导入保留正确顺序。避免多层再导出隐藏依赖。
- 颜色、字号、间距、边框与焦点样式优先复用 CSS 设计变量；新增样式按组件或业务职责命名，避免无范围覆盖。
- 桌面和窄屏均应可完成核心操作。按钮和输入项提供可读标签，支持键盘操作和可见焦点；对话框处理焦点进入、退出和恢复，异步反馈提供适当的可访问提示。
- 动画尊重 `prefers-reduced-motion`。按实际构建和性能数据决定懒加载、虚拟化或节流，不为优化增加无必要复杂度。
- 用户输入、商店文案和外部错误均按不可信内容处理；不直接插入原始 HTML。确需富文本时使用明确允许列表及清洗方案。
- 浏览器存储、URL、控制台、埋点和错误提示不得包含商店密钥、Token、Cookie、私钥或执行器秘密。未来认证方案按架构另行落地，不用前端长期令牌存储替代设计。

## 6. 中文注释规范

### 6.1 文件头与公开接口

所有新增手写 `.ts`、`.tsx` 文件，以及实际修改到职责或行为的既有文件，必须在首个 `import` 前提供 `@description` 文件头；生成文件、第三方代码和纯再导出入口除外。说明维护主题；页面、业务 Hook、API、Store 和公共基础设施还说明职责、数据来源以及权限或副作用边界。

```ts
/**
 * @description 项目列表的查询与创建交互
 *
 * 维护列表、表单草稿和提交状态；HTTP 协议交由 API Service 处理。
 * 创建失败保留用户输入，项目归属由服务端确定。
 */
```

新增或实际修改的导出组件、Props/Options 类型、Hook、Hook 返回对象类型、API Service、公共工具、Store、跨模块常量和配置，必须紧邻提供中文 JSDoc。说明用途和实际存在的关键参数、返回值、错误、前置条件或副作用，不机械重复名称。

Props 字段逐项说明；跨文件 Options、回调和复杂请求参数说明默认、省略及触发语义。`canPublish` 等属性须明确仅控制界面。文件内私有简单组件、类型和自解释赋值不逐项强制注释。字段注释可采用简洁单行 JSDoc，不要求重复类型已经表达的内容。

### 6.2 复杂流程与长度

三个及以上业务步骤、多个顺序依赖的异步调用，以及权限、上下文切换、竞态、缓存失效、状态转换、错误兜底和敏感信息处理，必须在职责最近处解释业务原因与边界。线性流程使用连续编号的 `// 1. ...`、`// 2. ...` 标注阶段，一个阶段覆盖完整逻辑块；非线性规则说明约束与拒绝原因。

| 函数有效代码行 | 注释与拆分要求                                                   |
| -------------- | ---------------------------------------------------------------- |
| 少于 30        | 不因长度强制分段；高风险规则仍须说明。                           |
| 30～59         | 存在两个以上控制流或异步业务阶段时，连续编号说明主要阶段。       |
| 60～99         | 连续编号划分主要流程，通常不少于三个阶段，并评估拆分。           |
| 100 及以上     | 默认拆分；确需保留时写明“长函数保留原因：”，继续按业务阶段说明。 |

有效代码行不含签名、空行、注释、纯类型及排版行；JSX 中有实际渲染或条件含义的行计入。不得以碎片函数或模板注释规避职责整理。普通 JSX 不添加无价值区域标题；复杂条件和不直观响应式重排才说明原因。

| 位置                | 最低说明                                                    |
| ------------------- | ----------------------------------------------------------- |
| 页面                | 文件职责、数据来源、主要状态和导出组件用途。                |
| Hook                | Options、返回约定、异步竞争与清理；引入缓存后说明失效策略。 |
| API Client、Service | 公开合同、错误、取消和安全边界。                            |
| 公共组件            | 组件用途、Props 字段和回调时机。                            |
| Store               | 状态所有权、持久化、重置和跨页面影响。                      |
| 测试                | 被保护的业务行为；复杂场景说明边界。                        |

TODO/FIXME/HACK 必须包含责任人或角色、日期和退出条件，例如 `TODO(前端维护者, 2026-11-03): 接入真实任务查询合同后移除规划占位。`。禁止复述代码、复制过期说明或写入秘密。行为变化同步更新注释，许可证、工具指令、协议固定文本和生成内容保留原格式。

## 7. 验证与 AI 执行要求

1. 修改前读取根目录 `AGENTS.md`、`README.md`、`CONTEXT.md`、`docs/ARCHITECTURE.md` 和本规范；涉及公开合同或跨端流程时同时读取[后端规范](backend-code-standards.md)。
2. 新增代码与实际修改范围遵循本规范；发现历史问题时只整理与任务相关的部分。新增文件、导出和复杂流程在完成时一并检查中文注释。
3. 使用现有测试工具；优先验证用户可见行为、错误恢复和跨层合同，不为简单展示写镜像实现测试。测试只用合成数据，不调用真实商店提交。
4. 完成变更运行 `pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm format:check`。页面变更还运行 `pnpm test:smoke`，并按变更补充真实浏览器检查，关注创建、失败反馈、刷新持久化、导航、键盘和窄屏布局。
5. 交付说明列出实际修改与验证结果。未运行、失败或环境阻塞的检查如实说明；本地测试不得被描述成远端发布验收。

目前类型、测试、构建和格式检查已有脚本；尚未建立 ESLint、注释结构或模块边界自动检查。上述规范仍是必须遵守的开发与评审约束，不能声称已有自动门禁。
