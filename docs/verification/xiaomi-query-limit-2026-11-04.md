# 小米执行前重复查询与状态显示修复

日期：2026-11-04。

## 用户现象与历史事实

用户看到计划历史的绿色“授权已消费”，但小米后台没有提交记录。本机对应 16:29:56 的计划在 16:30:22 结束为 verification_failed，原因仅记录 xiaomi_submission_validation，remoteStartedAt 为 null：没有获得上传许可，也没有确定的商店审核受理回执。授权消费只是本地一次性尝试登记，不是商店成功。

历史记录没有保存具体接口结果码，不能将后来探测的错误码反填进去。原失败、授权与取消记录保持不变，不自动提交或恢复旧授权。

## 只读诊断与原因

本机只读核对确认材料可读取、测试材料结构有效、目录版本未变化，安装包字节及图标摘要匹配、包名目标一致；原执行时刻在确认有效期内。

两组有界、只访问 /dev/query 的人工诊断均观察到：第一次 result=0 且名称匹配，紧接着第二次 result=-20035，供应商消息包含频率限制提示。没有读取或打印密码、SIG 或供应商正文，没有调用 /dev/push。

代码中 runRelease 先 checkMerchant，再调用 submitXiaomiUpdate；后者又查询同一目标。此重复路径可在上传前触发查询限频，与历史失败阶段一致。另有展示问题：计划已确认及授权被消费会显示绿色，未根据失败回执修正；执行列表也曾将小米成功统一标为草稿。

## 回归与修复

使用真实 aapt2 合成 APK、独立副本、内存安全库及受控网络，在完整 runRelease 调用链复现：首次查询成功、第二次返回合成 -20035。保留旧路径时 `pnpm exec tsx --test tests/xiaomi-runner.test.ts` 失败，安全计数为 queries=2、writes=0、permits=0。

修复后，小米目标核对统一归适配器负责，执行器继续独立验证计划、字节、副本、身份、目录版本与许可。该回归通过，queries=1、writes=1、permits=1；这是合成端口结果，不是真实提交。

查询限频增加固定 query_rate_limited／merchant_rate_limited 投影，并细分材料、目标、字节及许可阶段。没有增加上传或查询自动重试。计划列表、摘要及执行记录优先显示真实结果：提交前失败且未上传、小米已提交审核、华为草稿或待核对；授权消费不再充当绿色成功状态。摘要可直接查看原执行原因。
