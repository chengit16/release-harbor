# 第五期：本机团队工作台

2026-11-11 用户确认：团队工作台部署在自己的 Mac，成员在原工作台登录；管理员配置应用和商店账号，并为成员分配菜单、应用、渠道及操作权限。此方案取代[独立在线控制台计划](phase-5-hosted-console-plan.md)的实施顺序；已完成的在线验证入口保留隔离，不作为本机团队入口。首版只开放同机回环；成员从其他设备访问时另行设计内网入口。无需组织身份服务、公网域名或对象存储。

| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T0：边界       | 原工作台保持现有数据和发布安全规则；启用团队后既有业务入口全部经过认证，旧单人宿主不得继续服务同一数据根。                                                                |

| T2：审核与授权 | 管理员按成员配置菜单和应用／绑定范围，分别授权缓存读取与显式官方查询。直接接口和列表均检查归属，禁止用隐藏菜单代替授权。                                                  |

管理员接管现有数据，无须迁移应用、重录商店材料或另建发布执行器。同一业务数据根继续限定一个本机宿主；旧版本及旧隧道需在启用前停止。账号和会话在安装级保护目录及进程内维护，不纳入业务备份。成员只使用已绑定的商店账号执行获准动作，Web 不提供凭据回读。

## 成员权限验收例

管理员给小李开放「审核状态」，授权应用 A 的华为绑定查看缓存，关闭官方查询。小李只看到这一绑定，刷新不访问商店；直接请求应用 B 的 URL、上传包、查询官方或修改绑定均被拒绝。管理员开启 A 的官方查询后，小李才可显式查询，范围不扩到应用 A 的其他渠道。菜单撤销后旧链接也不能继续访问。授权同时绑定完整渠道配置指纹；账号、商店目标或绑定版本变化后需要管理员重新分配。准备、查询、确认执行和人工核对分开授权，Apple 上传、已有构建送审和批准后手动发布也分别区分。批次须完整获准才可一次确认，后台队列在获得每项写许可前重新核验成员资格。

发布另行授权：准备不能等同确认，确认只能覆盖授权绑定。多渠道批次中任一目标越界时整次确认失败；发出实际写许可前再核对成员、授权、摘要和原目标保护。记录操作人的身份和当时的动作，不保存登录口令、商店密钥或浏览器会话。此前无成员标识的历史维持原貌。
