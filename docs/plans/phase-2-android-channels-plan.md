# 第二期实施计划：Android 渠道逐个接入

**编制日期：**2026-11-04。

**状态：**P2-0 华为公共入口简化已完成工程实现，小米仍在规格准备阶段。

**用户优先级：**先完成本轮 Android 渠道，再恢复 iOS，应用宝与华为鸿蒙最后单独安排。本计划不把暂缓的 Apple 工作标记为完成，也不改写既有真实执行事实。

## 1. 确定的交付顺序

| 顺序 | 渠道                       | 本轮安排                                                 | 当前状态               |
| ---- | -------------------------- | -------------------------------------------------------- | ---------------------- |
| 基线 | 华为 AppGallery（Android） | 保留已交付的草稿、执行诊断及人工核对能力                 | 用户已确认后台看到草稿 |
| 1    | 小米                       | 当前首个开发切片，先明确账号、应用查询与更新提交语义     | 规格准备，未实现       |
| 2    | OPPO                       | 小米切片完成并核对后再开始                               | 待接入                 |
| 3    | vivo                       | OPPO 后开始                                              | 待接入                 |
| 4    | 魅族                       | vivo 后开始                                              | 待接入                 |
| 5    | 荣耀                       | 魅族后开始，与华为使用独立账号及目标                     | 待接入                 |
| 6    | iOS／Apple                 | 上述 Android 渠道完成后恢复上传适配与验收                | 暂缓，未完成           |
| 最后 | 应用宝、华为鸿蒙           | 上述 Android 与 iOS 渠道完成后另排，二者内部顺序届时确定 | 暂不开发               |

“最后”指本轮渠道接入优先级，不将华为鸿蒙与已有 Android 华为草稿混为同一能力。批次和并发属于后续交付增强；当前每次只开发、验证一个渠道，不同时展开五家。

## 2. 日常发版的统一操作

用户要求减少手动步骤。开发时逐渠道适配，不能让用户每次发版重复研究平台接口或逐项操作技术流程。

**目标交互：填写渠道、安装包和资料 → 准备发布 → 看摘要并确认一次 → 查看执行结果。**

- 账号初次配置后按渠道复用，不要求每次重新录入。
- “准备发布”自动核对已有产物、运行只读查询并准备不可变快照；此时没有商店写入。
- 摘要展示目标、版本、资料变化及真实动作；按钮明确写“确认保存草稿”或“确认提交审核”，只保留一次明确执行确认。无需先手动“冻结”，再“确认”，再“执行”。
- 检查失败在同一页面显示原因及修复入口，修复后原地重新准备，不要求跨多个页签。
- 确认过期或关键内容变化时在原页重新准备并展示最新摘要，不能延用旧确认或静默执行。
- 后端仍核对摘要、有效期、账号版本、产物、一次性消费及独立执行；减少的是手动操作，不取消这些规则。

### P2-0：先简化公共发布入口

先复用已经验收的华为链路验证上述交互，再接入小米。定义“准备”和“确认执行”的控制面用例；确认与一次性消费采用原子去重，不能把现有两次网络请求简单串联后就宣称一次确认已可靠实现。后续所有渠道沿用同一入口，渠道差异留在资料与动作适配中。

P2-0 已实现自动准备、进度恢复、单次确认与原子授权消费，完成隔离自动化和 Chrome 验证，见[验收记录](../../openspec/changes/simplify-release-flow/verification.md)；真实商店上传未在本轮重复验收。下一步按既定顺序接入小米。

## 3. 单渠道的推进方式

以下是开发与验收阶段，不是要求用户每次发版逐项点击的操作步骤。每个渠道依次完成，上一阶段的事实不得替代下一阶段的验收：

1. **能力核对与规格**：核实官方接口、SDK 真实行为、凭据、产物格式、应用定位、动作及响应语义，形成独立 OpenSpec 变更。
2. **账号与商店绑定**：页面向导按渠道录入材料，安全保存并按渠道筛选复用；应用包名、商店目标与账号引用保持独立，不强行套用其他商店的 appId 规则。
3. **只读预检**：核对实际产物、账号与商店目标，只运行明确白名单的查询；无法验证就保留失败或无法验证，不以查询成功推断上传授权。
4. **计划与执行**：冻结该渠道的真实动作和资料，在统一摘要中明确确认一次后消费授权，独立进程复核后执行，保存安全回执与诊断。
5. **恢复与验收**：重复执行不重放，未知结果先核对；完成隔离自动化及真实浏览器检查，并在明确账号、目标、产物和授权下另做真实渠道验收。

当前渠道未完成的部分保持待办。若真实材料不足，则明确记录“工程完成／真实待验收”，不自动跳过当前渠道或并行启动下一家；需要调整顺序时按用户后续指令处理。不承诺缺少渠道材料时的固定工期。

## 4. 小米首个切片

### P2-1A：账号与绑定

- 增加小米账号向导，使用开发者邮箱、平台 API 访问密码和 RSA 公钥材料，不能把“私钥”标签误解为 Apple 的 `.p8`。
- 沿用独立本机配置进程、材料不经过普通 API、安全存储、重新核对／编辑／重新录入／删除及关联保护。
- 明确包名定位与商店公开标识的关系，不要求用户编造华为式数字 App ID。
- 拆除当前仅华为／Apple 的类型白名单时，同步公开合同、存储守卫、测试和页面，保持历史数据兼容；不预先开放其他未实现渠道。

### P2-1B：只读核验

- 在可信适配层实现小米查询所需的签名与安全响应投影，API 不接触 API 访问密码或 SIG。
- 查询端点白名单独立于华为／Apple；HTTP 方法不代表是否有写副作用，按具体接口职责限定。
- 首轮限定已存在应用的版本更新；明确确认目标包名与账号匹配、平台当前允许更新。新增应用、资料修改及自动猜测新增／更新不在首轮范围。
- 查询失败、包名被其他账号占用、响应缺失／冲突、当前不允许更新均不得进入执行。

### P2-1C：更新提交与回执

- 页面明确动作“小米提交审核”，不能显示“保存草稿”或泛化的“仅上传”。SDK 静态观察与官方资料见[小米能力核对](../verification/xiaomi-baseline-2026-11-04.md)。
- 具体所需资料先核实再实现：更新说明、图标，以及平台要求的结构化测试说明／登录材料等；涉及秘密的测试账号单独走受信任材料边界，不能放入公开计划、回执或日志。
- 非秘密资料在确认前固定内容及摘要；执行不能悄悄改用另一份图标、说明或账号。SDK 缺失或语义不符时集中在 provider 适配，不直接放行底层上传器。
- 继续一次性授权、全局串行执行、产物副本复核、远端许可持久化及结果不明核对。成功只表示确定的受理事实，不等于审核通过或上架。
- 自动化不调用真实商店，不重试不明的提交审核动作；真实写入由用户对具体计划显式触发。

## 5. 后续渠道及批次

OPPO、vivo、魅族、荣耀在轮到各自切片时重新核实接口和资料，独立定义账号、动作、允许状态与回执；目前不宣称它们已可发布。不能因 SDK 导出同名上传器就复用小米的字段或动作语义。

单渠道逐个交付后，再按实际使用需要安排批次模型、渠道产物分配与受限并发；成功目标不重复提交，未知目标先核对，重试只针对明确允许的目标。此处不预建通用队列或一次铺开多渠道页面。

## 6. 验收门槛

- 既有华为流程和历史数据继续可用；未实现渠道不出现可执行发布入口。
- 新渠道保持页面配置、账号筛选、完整归属、真实字节检查、限定确认和独立执行边界。
- 各渠道分别验证目标不匹配、材料错误、超期、重复点击、取消、网络故障、中断和未知结果；不重放不明送审。
- 工程提交前运行类型、测试、构建、格式检查；页面修改运行真实浏览器冒烟，覆盖桌面、键盘、窄屏和失败恢复。
- 真实渠道另行验收，保留脱敏计划、执行编号、时间、动作与证据来源，不能用合成结果标记渠道完成。

## 7. 本次计划交付边界

规划阶段先确定顺序与小米规格，后续 P2-0 已交付华为公共入口简化；没有开放小米写入口、恢复 Apple 未完成改动或代用户执行真实商店操作。小米业务代码与真实验收仍为下一开发切片。
