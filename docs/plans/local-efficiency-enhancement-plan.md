## 1. 方向与预期收益

前四期已形成应用配置、安装包检查、发布准备与一次确认、多渠道批次、官方状态查询和有限送审编排。本阶段先保障本机数据可恢复，再减少重复查询和关注结果的操作，继续服务单人、本机使用场景。

交付顺序为：**手动备份与安全恢复 → 自动备份 → 审核自动跟踪 → 状态变化通知 → 恢复与运行验收**。

| 目标         | 目前的问题                                 | 完成后的体验                                                   |
| ------------ | ------------------------------------------ | -------------------------------------------------------------- |
| 数据可恢复   | 需要自行寻找和复制数据，难以确认是否完整   | 页面创建备份、预览恢复影响、确认恢复，明确哪些内容需要重新配置 |
| 减少重复查询 | 用户反复进入页面逐渠道点击查询             | 对选定目标开启跟踪，服务运行期间按规则只读查询                 |
| 及时发现事项 | 审核拒绝、待手动发布等事项需要主动查看     | 站内通知集中提醒，点击定位具体应用、渠道及版本                 |
| 边界容易理解 | 容易把旧在架、缓存或查询失败当作新版本结果 | 持续显示版本归属、来源、查询时间、能力限制和跟踪运行状态       |

这是原六期路线之外优先落地的本地增强阶段，不改写原第五期、六期的定义，也不将其标为完成。第五期在线控制台与第六期完整团队自动化暂缓，待多人共享、远程执行或 CI 交接需求明确后重评。

## 2. 首版范围与取舍

首版包括本机业务数据备份与恢复、用户开启的每日自动备份、服务端只读跟踪、站内通知及可选浏览器通知。不增加数据库、Redis、云存储、远程执行器或常驻系统服务。

暂不包括团队登录与审批、远程控制台、预约上传／送审、自动发布、自动重送、商店回调接入、邮件／企业微信／钉钉通知、凭据导出和跨设备无缝迁移。商店已有定时上架和 Apple 自动／手动发布流程继续沿用。

不把“功能工程完成”当成真实商店状态、通知权限或无人值守运行已验收。

## 3. 页面与操作设计

### 3.1 菜单安排

| 入口                    | 内容                                                                   |
| ----------------------- | ---------------------------------------------------------------------- |
| 配置 → 本机设置（新增） | “备份与恢复”“通知设置”；展示本机服务运行说明                           |
| 发布 → 审核状态（现有） | 开启／暂停／结束跟踪，查询间隔、跟踪版本、上次及下次查询、异常原因     |
| 页头通知入口（新增）    | 未读数量、通知列表、标记已读和跳转；完整列表在本机设置的通知记录中查看 |
| 发布中心（现有）        | 保持发布发起与执行职责；送审成功后提供“开启审核跟踪”，默认不勾选       |

采用现有白色主题和 Ant Design 组件。备份、恢复及跟踪配置均可在页面完成，日常操作不要求用户进入终端。桌面表格与手机卡片使用同一状态文案及标签；页头、筛选、按钮和内容左边缘按现有规范对齐。

### 3.2 核心操作

- 备份：进入本机设置 → 创建备份 → 查看完成结果和范围 → 按需下载到其他位置。
- 恢复：选择备份 → 校验及预览 → 查看覆盖、缺失材料和安全限制 → 明确确认 → 显示恢复结果。
- 跟踪：进入审核状态 → 选择商店绑定及可定位版本 → 设置间隔、结束条件 → 开启跟踪。
- 通知：查看未读提醒 → 点击进入原审核状态详情 → 按需到官方后台处理，或回发布中心准备新的明确动作。

## 4. 备份与恢复

### 4.1 备份范围

| 数据                                             | 首版处理                           | 恢复后的含义                                                 |
| ------------------------------------------------ | ---------------------------------- | ------------------------------------------------------------ |
| 项目、应用、商店绑定                             | 纳入白名单                         | 恢复配置，不证明账号有效或目标可执行                         |
| 商店账号名称、引用等安全元数据                   | 仅纳入可信配置进程投影的非秘密目录 | 与本机现存档案重新核对；不直接覆盖可信凭据目录               |
| 发布计划、批次、执行回执、人工核对、版本保护事实 | 纳入业务历史                       | 保留原始事实与摘要；授权不能因恢复重新可用                   |
| 状态缓存、查询历史、资料检查和待办来源           | 纳入现有安全投影                   | 保留原时间、来源及非实时说明，不自动查询                     |
| 安装包身份、版本、大小与摘要                     | 纳入元数据                         | APK／IPA／APP 字节不随首版备份保存；文件缺失时重新导入并校验 |
| 跟踪与通知设置、通知记录                         | 相应功能交付后纳入                 | 恢复后跟踪暂停，历史通知不重新推送                           |
| Keychain、Vault、私钥、Token、测试账号、配置会话 | 排除                               | 仍由可信本机配置流程管理；缺失时重新配置                     |
| 原始日志、临时文件、仓库和问题档案构建资源       | 排除                               | 不属于用户运行数据备份                                       |

备份是业务数据副本，不是整机镜像。恢复预览必须明确“不包含账号秘密与安装包原文件”，不能只提示“备份成功”而隐去范围。备份可能含应用名称、更新说明等业务资料，应提示妥善保存；不包含秘密不等于不敏感。

采用带格式版本的受限数据容器，记录备份 ID、产品版本、创建时间、各模块 schema、数量、大小和 SHA-256。摘要用于损坏检测，不作为备份来源认证或加密证明。首版不提供密码加密，备份保存在受限本机目录，下载前展示业务数据提示；加密导出另行评估。

### 4.2 一致性与创建规则

- 不直接打包整个数据目录；按明确白名单导出，新增存储模块须登记是否备份及恢复依赖。
- 使用统一维护门禁覆盖配置、上传、准备、许可、回报、状态缓存和后续自动任务。进入一致性点前排空相关写队列，不用逐个复制正在变化的文件冒充一致快照。
- 有活动发布、批次、安装包导入或账号配置时不强行备份／恢复；页面说明当前阻塞操作。跟踪查询先暂停调度，已有请求完成或安全结束后才进入维护。
- 文件先写临时位置，校验完成再发布为可见备份；磁盘不足、校验失败或进程中断不能生成“成功”记录。
- 默认不启用自动备份。用户开启后建议每日一次、保留最近七份成功的自动备份；自动清理不删除手动备份和用户导出的文件。目录和保留数变更须校验，不能接受任意路径读写能力。
- 应用关闭、休眠时不执行；重启后最多补一次到期备份，不追补所有错过的周期。同盘备份便于回退，但不能防磁盘损坏，页面提供导出到其他位置的入口。

### 4.3 恢复策略

首版采用**整套业务数据替换恢复**，不提供逐项目或逐记录合并，避免出现应用、绑定、计划和回执之间的悬空关联。已受理版本和未知执行的安全保护事实另行保留并保守合并，不随旧业务快照回退。

1. 先校验容器、大小、条目数量、格式版本、模块 schema、摘要、记录归属和跨模块引用；新于当前程序支持的格式拒绝导入。解析过程拒绝路径穿越、符号链接、重复条目及超限展开，不按备份内容执行代码或访问路径。
2. 展示当前数据与备份的数量差异、日期、缺失凭据／安装包、覆盖范围和恢复后的限制。预览只读，不触发商店查询。
3. 明确确认后再次核对预览指纹和当前数据版本；变化时要求重新预览。进入维护门禁，先生成当前数据的恢复前快照；已有数据损坏且不能可靠保护时拒绝普通覆盖，进入单独诊断流程。
4. 在隔离目录校验恢复结果，再以可恢复的整代切换发布全部业务数据；不把多个文件逐次覆盖视作原子恢复。中断后按持久化恢复日志选择完整的一代，禁止启动混合新旧数据。
5. 清除可执行会话及查询预约的运行资格。旧摘要和原始历史保持不变，通过独立恢复屏障让旧预检、确认及排队任务不能再执行；需要重新准备与确认。
6. 展示恢复报告。账号引用重新匹配可信目录，安装包重新检查；不自动续跑发布、开启跟踪、查询商店或补发通知。

### 4.4 防止旧备份绕过发布保护

这是 L0／L1 的交付前置条件，不能等普通恢复完成后再补：

- 同一安装保留独立于可替换业务快照的安全保护账本，覆盖已消费授权、已受理版本、写入许可及未澄清结果。接入时核对现存历史并保守初始化；许可发放与账本落盘须有一致恢复协议。
- 恢复较早备份不能删除备份之后已知的成功版本或未知目标阻塞；两侧保护事实取保守并集，原始证据及来源分别保留，冲突进入人工核对。
- 账本缺失、损坏或安装身份不匹配时禁止恢复后直接发布。更换机器／整盘丢失场景先恢复为只读历史，配置材料并按目标完成官方或人工核对后，方可另行准备新发布；无法澄清的目标继续阻塞。
- 不以“恢复成功”自动证明商店没有处理中任务，也不允许复制备份使两台机器获得同一份可重放许可。首版不承诺跨机器发布锁或无缝迁移。

## 5. 审核自动跟踪

### 5.1 开启与目标范围

默认关闭。用户对确定商店绑定显式开启后，由本机 API 的调度服务调用已有固定只读 worker；页面 GET、刷新和导航仍只读缓存。实施时须同步更新当前“仅点击才查询”的约定，例外只限用户开启且仍有效的跟踪任务。

支持在没有本机发布记录的情况下开启。跟踪优先固定官方版本 ID、构建号或审核单；绑定指纹、查询范围和可用身份一起持久化。无法定位具体版本时，只允许标为“应用级观察”，不能承诺跟踪某个新包审核。

用户可选择“跟踪到审核结果”或“继续跟踪到上架”；首版默认到审核结果，默认七天到期并允许手动延长。拒绝、撤回及目标已上架时结束相应任务；Apple 待手动发布时生成待办并暂停，用户可显式改为继续观察上架。未知状态不作为成功结束条件。

### 5.2 调度与失败处理

- 建议默认间隔三十分钟，可选十五、三十、六十分钟；实际间隔取用户设置、已有渠道冷却与官方限额要求中的更严格值。上述数字是产品建议，不是官方配额。
- 首版全局查询并发为一；手动与自动查询共用目标预约和限流，避免两个入口同时请求。同渠道共享额度需统一控制，不能只做单任务节流。
- 显示“跟踪中／等待下次查询／退避中／已暂停／已结束／需处理”、最近结果时间及下次可查询时间；跟踪运行状态与商店审核状态分别使用标签。
- 网络或临时限流失败按有限退避处理，连续三次失败暂停并提醒；凭据、身份错配、权限、格式或未知响应等需处理错误直接暂停，不自动重录凭据。
- 服务关闭和电脑休眠期间不保证运行。服务重启或唤醒后重新核对任务、绑定、账号目录和冷却，仅安排一次到期查询并错开任务，不重放积压轮次。
- 绑定或账号材料变化后暂停；重新确认目标才能继续。默认“最新版本”返回了其他版本时不偷换目标，记录无法定位并提示核对。
- 暂停和结束后不再派发新请求；已在途只读请求可保留结果，但不得因此重新开启任务。状态查询不改变发布授权、回执或人工核对。

### 5.3 渠道限制

复用现有官方能力和版本定位，不新增未经核实的状态字典。小米只能观察公开在架事实，不能生成“审核中／审核拒绝”通知；应用宝应用级审核与版本资料分开，通知注明不能关联确定版本。魅族缺构建号、荣耀当前流程范围等限制继续保留；Apple 审核员私人意见正文仍需官方后台查看。

只比较同绑定、同查询范围、可证明同一版本的成功结果。目录缺项不推断下架，旧在架不覆盖新送审，失败不生成状态变化；初次成功作为基线，不把历史结果伪装成刚发生的变化。首次已存在的拒绝／待手动发布事项可生成明确标注“首次发现”的一条提醒。

## 6. 通知与待办

首版必须交付站内通知，可选浏览器通知。浏览器通知仅在用户点击启用后申请权限；拒绝或不支持时仍可查看站内通知，不自动重复申请。

| 事件         | 提醒内容                                   | 点击行为                                 |
| ------------ | ------------------------------------------ | ---------------------------------------- |
| 审核状态变化 | 审核通过、拒绝、撤回等官方可证实变化       | 定位原绑定及版本，查看来源、时间和建议   |
| 待手动发布   | Apple 等待开发者发布                       | 查看状态并按需进入发布中心，仍需独立确认 |
| 上架事实变化 | 确定版本已上架；小米仅明确公开在架观察范围 | 打开该版本详情                           |
| 跟踪需处理   | 连续失败、凭据问题、目标变化或跟踪到期     | 打开跟踪设置或账号处理入口               |
| 备份异常     | 自动备份失败、磁盘不足、恢复失败           | 查看本机设置内的固定诊断与处理建议       |

通知持久化后再尝试浏览器展示，采用稳定事件 ID 去重。状态未变化不重复通知；同一失败事件合并计数，恢复正常后才开启新的异常周期。已读／未读与待办处理状态分别维护，标记已读不代表问题解决。

重启只恢复站内未读记录，不批量弹出旧通知。浏览器展示尽力投递，不承诺恰好一次或关闭浏览器后的系统推送；首版不引入 Service Worker 后台推送、系统登录项或常驻代理。API 运行而页面关闭时，可继续跟踪并积累站内记录；API 退出后停止跟踪。

通知仅保存安全摘要、目标定位、来源和观察时间，不包含密钥、测试登录资料、审核员意见原文或供应商原始错误。浏览器通知默认只显示通用事项，可由用户选择是否显示应用名称。通知深链仅负责定位，不携带授权或触发商店动作。

通知记录首版保留最近三百条，超限按最早记录淘汰，页面标注范围；查询历史仍遵守现有保留上限。通知与业务状态更新使用可靠事件登记，避免缓存写成功却永久漏掉事件；跨文件崩溃恢复和去重应有专项验证。

## 7. 架构与实现约束

- 延续单机单实例、回环地址及本机来源保护；不开放 hosted 或公网访问。
- 备份协调器管理一致性点、白名单和恢复代切换；秘密目录由可信配置服务负责，不交给通用 API 打包或覆盖。
- 跟踪调度只派发受限的状态读取任务，无发布写许可，也不能调用确认、上传、送审或发布接口。SDK、凭据与官方网络留在可信 worker。
- 使用现有 JSON 存储模式增量设计备份索引、恢复日志、安全账本、跟踪任务和通知记录；文件名、schema 和公开 API 在相应切片落地前确定，不在规划中宣称已实现。
- 各存储继续版本校验、串行写队列、原子替换及损坏拒写。恢复门禁、定时任务和现有发布许可入口须共享必要的准入控制。
- 备份创建／导入、恢复确认、跟踪启停及通知设置均为受保护写操作；恢复确认绑定预览内容，不接受浏览器直接提供服务器任意绝对路径。

| ---------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **L0：数据盘点与恢复协议**   | 运行数据白名单、schema／归属依赖、账号边界、防回退账本和维护门禁设计 | 明确恢复前后每类数据语义，并用专项设计核对证明旧备份不能恢复发布许可；未通过不进入恢复实现       |
| **L1：手动备份与恢复**       | 本机设置、创建／下载、导入校验、预览确认、恢复报告及整代切换         | 干净目录演练与同机旧备份恢复通过；坏包拒绝、覆盖可回退、秘密排除、历史摘要不改写；新机器默认只读 |
| **L2：自动备份与恢复演练**   | 用户开启的每日备份、七份保留、失败记录及恢复前快照                   | 休眠／重启不重复补跑，手动备份不误删；磁盘不足或中断不损坏当前数据，可恢复上一完整代             |
| **L3：审核自动跟踪**         | 跟踪启停、目标范围、间隔、结束条件、共享限流、退避与持久化           | 无本机计划也可跟踪；刷新零派发；同版本比较、不偷换目标；休眠／重启和失败可解释，零商店写入       |
| **L4：站内与可选浏览器通知** | 事件登记、去重、未读入口、通知记录、设置和深链                       | 一次变化生成一条站内事件；首次发现有标识；权限拒绝可用，重启不补弹；点击不直接发布               |
| **L5：文档与完整验收**       | 操作指南、问题档案、路线图、备份恢复和运行限制说明                   | 适用工程检查、桌面／手机浏览器和故障演练通过；真实渠道另按明确目标验收                           |

每个切片单独交付和验收后再推进；L1／L2 完成即可先用于数据保护，不必等待跟踪和通知。若备份范围或安全账本使恢复成本超出预期，先交付可验证的备份导出与只读恢复，明确缺口，不降级为可重放授权的目录覆盖。

## 9. 验证要求与成功判断

工程验证至少覆盖：跨文件一致性、损坏／新格式备份、超限输入、路径攻击、写入中断、旧备份防回退、凭据和安装包缺失、同目标并发查询、限流、时钟变化／休眠恢复、绑定变更、通知去重及旧数据兼容。

测试使用合成账号、临时目录、可控时钟和替身网络，不读取真实 Keychain、Vault 或用户业务目录，不发送真实商店写入。按项目要求执行 `pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm format:check`；页面变更另执行真实浏览器冒烟，验证对齐、标签、窄屏、刷新、深链及拒绝通知权限场景。

真实验收由用户明确选择应用、渠道及范围后开展：至少完成一次备份导出与隔离恢复演练、一项可定位版本跟踪和一次本机通知验证。没有自然发生的审核变化时，可用合成事件验证通知链路，真实状态变化继续标待验，不通过送审制造测试数据。

成功标准是：用户能从页面恢复可核对的业务记录，旧备份不能绕过发布保护；服务运行期间无需反复手动查询便能发现受支持状态变化；通知能定位待处理事项，同时准确说明渠道、版本和本地运行限制。

## 10. 后续重评条件

多人共同发版、多设备共享记录、远程执行或 CI 交接成为实际需求时，重新评审第五期最小在线版。团队审批、无人值守预约执行和外部通知再按第六期单独确定身份、授权与恢复合同。本地跟踪开启不构成这些动作的授权。

当前下一步建议为评审本方案；确认实施后从 L0 开始，再进入 L1，不同时铺开全部模块。
