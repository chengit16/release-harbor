# 多渠道发布批次实施方案

**日期：**2026-11-06。

**状态：**规划完成，功能尚未实现。用户已选择首版范围为“同一个 Android 应用的多商店”。

**依据：**[第二期安排](phase-2-android-channels-plan.md)、[领域术语](../../CONTEXT.md)、[架构](../ARCHITECTURE.md)及[本次规格](../../openspec/changes/add-android-release-batches/proposal.md)。

## 1. 首版交付

用户在一个 Android 应用里选择多个已绑定商店，为各商店分配 APK，填写统一或独立更新说明与上架方式。系统自动逐项准备，用户核对一份完整摘要、明确确认一次，系统逐渠道执行并集中展示结果。

首版包括华为 AppGallery Android、小米、OPPO、vivo、魅族、荣耀和应用宝，最多七项，每家一项；一个目标仍只执行一个已检查的 APK。华为仍保存草稿，其余维持各自既有更新提交动作。新批次不改变渠道资格、版本递增、材料复用及真实验收范围。

| 首版包含                                      | 首版不包含                                       |
| --------------------------------------------- | ------------------------------------------------ |
| 同一工作空间、项目和 Android 应用内选多个渠道 | 跨项目、跨应用、iOS／鸿蒙混合批次                |
| 一个 APK 复用到多渠道，或每渠道分配独立 APK   | APK 自动构建、渠道包加工、双包上传、新商店接入   |
| 统一说明及上架默认值，每行可明确覆盖          | 静默截短说明、忽略不支持的策略或自动改为立即上架 |
| 自动准备、一份摘要一次确认、后台串行执行      | 首版并行商店写入、通用队列平台、预约开始上传     |
| 独立回执、停止后续项、失败项重新准备          | 自动重复送审、重放未知结果、撤回已发生的商店操作 |

第一交付使用全局写入并发 **1**。受限并发 2 是后续独立切片，需在批次恢复及逐渠道真实证据具备后另行确认；本次不把它标为完成。百度按已完成的可行性核对不纳入。

## 2. 日常操作

```mermaid
flowchart LR
    A[选择渠道] --> B[分配安装包与说明]
    B --> C[准备批次]
    C --> D[核对一份摘要]
    D --> E[确认执行 N 个渠道]
    E --> F[逐渠道执行与结果]
```

### 2.1 入口和配置

保留应用工作台的“发布计划”页签，在页内切换“单渠道／多渠道批次”，不增加全局菜单。现有单渠道历史和入口继续可用，批次草稿、历史和详情按当前应用隔离。URL 可记录 `tab=plans&releaseView=batch&batch=<id>`，不放凭据、表单秘密或执行许可。

页面采用白色 Ant Design 布局，使用 Form、Table、Select、Checkbox、Descriptions、Drawer、Tag、Alert 等已有组件。桌面以渠道表格配置，手机每渠道一张卡片；摘要和进度保留完整渠道名、目标和版本，技术指纹按需展开。

- 渠道默认不勾选，提供“选择全部可用渠道”；缺少绑定或账号的渠道显示原因及现有配置入口。
- 公共区域选择发布版本、通用 APK、更新说明和上架默认值；“应用到已选渠道”是显式操作，不覆盖未选渠道或历史快照。
- 每行展示商店、真实动作、数字 App ID／包名、账号标签、APK 文件与版本、说明／上架覆盖值及准备状态。
- APK 必须属于当前应用、状态 ready、包名匹配；不凭文件名猜测渠道。允许复用同一 artifactId，不重复上传到本机；每次商店执行仍创建独立副本。
- 同批所有 APK 的 versionName 须一致，以免一次确认混入旧版本；buildNumber 可以不同，但摘要逐项展示并按渠道校验递增条件。不同版本须另建批次。
- 统一说明仍逐行执行渠道长度和内容规则；不自动截断。魅族遇到指定时间时显示冲突，用户须明确改为立即或移除该项。华为草稿的上架选择仅记录意图。

### 2.2 准备和摘要

“准备批次”在后台执行只读检查，不确认、不上传。首版仍共用现有全局单准备槽，逐项检查并在通过后立即冻结该项计划；不直接并发调用当前会返回 busy 的预检接口。

每次准备产生独立 revision。全部检查结束后展示各项成功、失败及原因；失败不吞并成全局泛化错误。全部就绪时自动打开一份摘要，列出确切渠道集合、顺序、真实动作、版本、账号、文件和 SHA、说明及上架选择。

部分失败不自动少发几个渠道。用户可修正失败行重新准备，或明确移除失败行后重新生成摘要；产生新的 revision 和摘要，未过期且意图完全相同的只读事实可复用，其他重新检查。准备期间和摘要页面关闭都不会产生商店写入。

摘要显示五分钟的**本次复核确认窗口**，起点为摘要完成时间；逐项保留原检查时间，过期的检查显示“待执行前复核”，不冒充当前仍有效。这个窗口不是复用旧单渠道预检取得写权限：批次写入必须另外通过第 4 节的临执行复核与批次授权。

### 2.3 一次确认与结果

摘要勾选项明确包含渠道数量、部分华为草稿／其他更新提交的动作差异，以及批次开始写入时限。按钮为“确认执行 N 个渠道”，不使用“全部上架”。确认成功返回批次执行编号，后台按冻结顺序逐项处理，刷新或关页仅影响查看。

批次概览给出就绪、排队、复核、执行、已完成、未执行失败、待核对及停止数量；每行保留真实原始回执。全部结束只表示这些操作已经结束或得到受理事实，不表示商店全部审核通过。部分失败、部分成功和未知结果可同时展示。

“停止后续执行”立即撤销未授予远端许可的剩余项；已获许可的当前项继续保存结果，不据此声称撤回。停止后不保留自动续跑开关。

## 3. 当前实现约束

| 现状                                                                   | 对方案的约束                                                              |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| ReleasePreparationsService 和 PreflightsService 都只允许一次准备       | 不能把多个 HTTP start 用 Promise.all 包装成批次；需要统一登记和逐项编排。 |
| 单渠道 PlanAuthorization 为 local_once，最多五分钟且不晚于原预检有效期 | 不能一次确认七份旧授权后长时间排队，也不能在后台悄悄续期。                |
| ReleaseExecutionService.start 原子确认、创建尝试并立即启动子进程       | 需抽出共享的登记与派发边界，批次排队项不能直接伪造七个进行中尝试。        |
| FileReleasePlanStore 同文件还保存 appleReviews，未完成执行总数不超过 1 | 批次与单渠道、Apple 审核共用写入协调及恢复；不能各开一套独立槽。          |
| runner 及 provider 直接校验 ReleasePlan 的单次授权                     | 需显式增加批次证明和统一执行上下文，不能伪造一个“已确认的新单渠道计划”。  |
| 历史未知与成功产物已有跨计划目标保护                                   | 新批次／新 revision 不得绕过原保护。                                      |

## 4. 批次确认与临执行证明

以下是**拟新增的批次合同**，不修改单渠道 local_once 的五分钟规则。

1. 用户只确认服务器生成的 batchId、revisionId、batchDigest、完整目标集合和顺序。摘要超过五分钟须重新准备／展示；不能允许浏览器指定延长时间或增加目标。
2. 同一事务写入 `BatchConsent(scope=local_batch_once)`、确切目标集合、一次批次执行记录及预约目标。**建议首版开始写入窗口为确认后 60 分钟**，服务端固定且摘要明示；更改该值需要修改规格与验证，不能由页面放大。
3. 各目标临到执行时才创建一个 attempt、占用全局执行槽。worker 重新核对原始快照指纹、绑定／账号版本、原件和独立副本，再完成本渠道已有的只读目标及来源检查；不能仅凭排队时的旧预检。
4. 临执行检查只允许验证同一冻结意图。对已有渠道来源锚点逐字段比对；原有华为草稿只按已实现的目标、账号及字节范围核对，不宣称新增了审核状态查询。任何关键来源、版本、材料、目标或配置变化都不得自动替换快照。
5. worker 通过带版本、nonce 和严格白名单的私有消息报告 `BatchTargetValidation`。控制面验证其批次、目标、attempt、快照摘要和检查范围，事务保存证明与 remoteStartedAt，随后才回传一次 grant。
6. 开始写入须同时满足：批次未停止、该目标尚未消费、原预约有效、临执行检查距现在不超过五分钟、未超过 60 分钟窗口，以及指定上架时间仍在未来。证明不包含秘密，也不是浏览器可提交的许可令牌。
7. 60 分钟限制的是首次远端写入的开始时点。已获许可的单次链路继续遵循已有至多 30 分钟 worker 上限及每步账号／上架时间检查，不因窗口耗尽自动重传。超过窗口但未开始的目标进入“需重新准备”，只对剩余项生成新意图并明确确认。

准备的旧预检事实及子计划保持原值；新的临执行证明独立追加，不重写 preflight 时间、计划摘要或单渠道授权。provider 的同一段目标查询须同时服务来源比对与执行证明，不额外再发一次查询触发限流。SDK 内部仍须明确禁用不明写重试。

需在可信 Node 内将各 adapter 的必要参数整理为 `StoreReleaseContext`：冻结 snapshot、来源类型、预期账号版本及开始写入边界。单渠道与批次分别经过权威入口构造该上下文，provider 不负责签发授权；Web/API 不加载 SDK。现有直接接收 ReleasePlan 的接口保留兼容包装，避免一次改坏已验收渠道。

## 5. 模型和持久化

| 拟新增对象            | 职责与不变量                                                                                        |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| ReleaseBatch          | 当前应用内的公开草稿及 revision 集合入口；有乐观并发版本，不包含秘密。                              |
| BatchRevision         | 一次完整准备的固定目标集合、顺序及规范化说明／策略；准备结束后不可编辑，确认前改动产生新 revision。 |
| BatchTarget           | 对应一个绑定和一个 APK；保存准备状态、preparation／plan 引用、摘要、目标及原始检查时间。            |
| BatchConsent          | 一次用户同意，绑定 revision、batchDigest、确切目标集合、顺序、固定开始写入窗口；不续期。            |
| BatchRun              | 一次确认的执行与停止事实；派生总览，不伪造跨商店事务成功。                                          |
| BatchTargetValidation | 每次实际目标复核的安全证据，关联 planDigest、账号版本、检查时间、范围和对应 attempt。               |
| ReleaseAttempt.origin | 可选的批次来源标识；旧记录缺失继续按单渠道解释，不改历史事实。                                      |

批次准备通过时，在同一事务插入未授权子计划并建立批次归属；批次子计划不能走旧接口单独确认执行。子计划仍保留原 snapshot 和 digest，批次授权不把它伪装为 local_once 确认。

拟将现有 release-plans.json 从 schema12 升级到 schema13，新增 `batches` 聚合，保留 `plans`、`attempts`、`preparations`、`appleReviews`。恢复兼容 1–12，旧记录不回填批次字段、不重算指纹。批次归属、引用完整性、目标唯一性、授权消费和尝试关联必须在读写两端校验。

确认、预约、attempt 创建、首次写许可及终态更新都经同一原子替换队列；拒绝 JSON 损坏、未知版本和不完整关联，不降级为空库。预检事实仍可在独立事实文件中保存，跨文件不明时最多产生没有授权的检查，不能产生孤立写权限。不新增依赖或独立 batch JSON 事务。

## 6. 执行、失败和恢复

- **写入并发 1**：确认批次后仅保存排队目标，不能提前创建七个 preparing attempt。单渠道、批次和 Apple 审核／手动发布共用同一个执行协调器及存储不变量；活跃批次期间不插入其他写操作，新确认返回明确 busy，不自动替用户排另一个批次。
- **固定顺序**：摘要与执行顺序一致；修改顺序需要新 revision。逐项结束并成功落盘后才领取下一项；写盘失败立即停止调度。
- **预约和防重复**：批次确认时以 workspace、channel、商店目标键预约各项。已有运行、未知结果、成功的同一产物、其他批次预约及 Apple 现有保护共同生效；旧单渠道入口不能绕过预约。停止／耗尽／完成后释放未执行预约，历史成功与未知保护仍保留。
- **独立失败**：某渠道准备或执行失败不改写其他渠道事实；无依赖关系的其他渠道按原授权继续。未知项保持待核对，系统不重试该项；后续针对同一目标的操作仍阻塞，其他商店不因此伪装成失败。
- **重新准备剩余项**：只明确选择未执行或许可前失败项；未知项须先人工核对，确认未受理且没有处理中任务后才可创建新 revision。已成功或人工确认存在的同一产物始终不重发，不能绕过“结果不明”直接点重试。
- **已有事实不重算**：保留旧 batchRun、attempt、原结果和人工结论。所谓补发是新 revision、新确认和新尝试；历史中的成功项只读引用，不能复制到新队列。
- **停止竞态**：停止与 grant 在同队列竞争；停止先落盘则拒绝首次写入，grant 先落盘则视为远端可能已开始，保留当前项真实结果。页面关闭不是停止。
- **服务重启**：未完成准备标中断；已有 attempt 按 remoteStartedAt 分为执行前中断／待核对。原队列未开始的项标“重启后需重新准备”，撤销其预约，不在启动或 GET 中续跑。已消费的授权不复活。
- **进程隔离**：保持真实副本、固定 worker、nonce、超时和进程组清理。控制面不读取秘密；本期不支持多个 API 实例共享写入。

## 7. 拟新增控制面接口

前缀为 `/api/projects/:projectId/applications/:applicationId/release-batches`，workspace 仍由可信本机入口确定，不接受浏览器指定。

| 接口                                              | 目的                                                                                 |
| ------------------------------------------------- | ------------------------------------------------------------------------------------ |
| POST /                                            | 保存公开草稿；requestId 相同意图返回原批次，不同意图冲突。                           |
| GET /、GET /:id                                   | 当前应用批次历史、草稿和安全进度；不发商店查询或重放任务。                           |
| PUT /:id                                          | 按 expectedRevision 编辑尚未冻结的草稿；不修改历史 revision。                        |
| POST /:id/prepare                                 | 异步生成准备 revision，独立 requestId 去重，同一请求不重复检查。                     |
| POST /:id/revisions/:revisionId/confirm-and-start | 只接受 expectedDigest、requestId、acknowledged；同事务记录授权和批次执行，返回 202。 |
| POST /:id/runs/:runId/stop                        | 停止尚未获许可的后续项，幂等，不声明撤回远端操作。                                   |

所有写入口沿用严格 Host／Origin、本机标记、no-store 和精确字段校验。请求只接受公开引用及版本，平台动作由服务端依据绑定推导；不接收客户端声明的成功、商店来源、授权时长、并发数或执行路径。对旧单计划与新批次的直接请求都需覆盖来源、归属及绕过测试。

页面轮询仅读取持久化进度；准备和执行中建议一秒，空闲三十秒，并在卸载时取消请求。HTTP 响应丢失仅查询原 requestId；不得将客户端 fetch 重试变成重复写。

## 8. 实施拆分

| 切片              | 交付与建议提交边界                                          | 退出条件                                                                             |
| ----------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| B1 合同与存储     | 批次草稿、revision、来源／证明类型、schema13 兼容和严格守卫 | 旧 1–12 数据及 Apple 记录保持，坏关联拒绝，旧指纹不变。                              |
| B2 逐项准备       | 产物分配、逐渠道校验、批次准备及不可变摘要                  | 失败原因按行、部分失败不自动排除，零商店写入，响应丢失不重查。                       |
| B3 一次确认和执行 | 共享登记／派发协调器、限定批次授权、临执行证明、串行 worker | 一次确认只派发一次；超过原五分钟仍可在明示批次窗口内安全启动排队项，关键变化零写入。 |
| B4 结果与恢复     | 预约保护、停止、剩余项新 revision、单计划与 Apple 互斥      | 未知不重发，成功不复制，重启不续跑，停止与许可竞态有确定结果。                       |
| B5 页面和验收     | 原应用页内批次配置、一次摘要、行级结果、桌面／窄屏／键盘    | 从分配到结果的真实浏览器闭环，所有适用检查通过，明确真实商店待验收。                 |

每片先做合同／集成验证再接页面，不在中间提交开放无执行后端的危险按钮。B3 未通过时批次确认执行保持不可用，不回落到循环调用旧接口。现有单渠道回归持续保护。

## 9. 主要验收场景

1. 同一应用七渠道可分配同一 APK 或不同 APK，跨应用、IPA／APP、坏文件、不同 versionName、重复渠道均拒绝。
2. 全部就绪时摘要明确每行目标、真实动作、APK／构建号、说明及策略，一次确认只生成一次 batchRun。
3. vivo／荣耀说明超限、应用宝 Emoji、魅族定时及商店来源变化逐项报错，不静默修改公共输入。
4. 准备耗时较长、首行旧预检已过期时，不借旧事实越过许可；控制时钟超过五分钟但在批次窗口内的排队项必须完成新的复核及证明。
5. 把确认时钟推进到超过批次窗口、把定时时间推进到过去、修改账号／绑定／文件／已有来源摘要，都不得给该项新的远端许可；旧事实仍保留。
6. 重复确认、响应丢失、并发两个批次、单渠道／Apple 同时确认，以及批次子计划的旧执行路由，均不能产生重复或超额执行。
7. 某项成功、某项超时未知、某项许可前失败时，其他独立项继续；同目标未知操作和同产物成功操作不能重发。
8. 停止与领取、grant 同时发生、JSON 写入失败、worker 退出、API 重启及 HTTP 断连，不丢原事实、不自动重放。
9. 修改公共默认值、移除失败行、补齐材料后重新准备，只影响新 revision；成功项和老摘要不变。
10. schema1–12 升级、坏关联、缺少批次记录、旧摘要校验及 Apple 审核历史恢复均覆盖；不更新历史授权时间。
11. 浏览器在桌面和 390px 完成选择、分配、失败修正、一次确认、停止、查看结果、剩余项新准备和刷新，密码不进入普通 API、URL 或页面存储。
12. 执行 `pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm format:check`；页面实现后运行 `pnpm test:smoke`。自动化仅隔离数据和注入网络，真实多渠道提交另由具体批次的明确用户确认验收。

## 10. 本轮边界

本轮只完成范围确认、现状核查、设计、规格和任务拆分；不新增运行入口，不迁移用户存储，不消费授权，不访问真实账号或商店。工程与真实验收状态不得因规划完成而更新为已交付。后续按 B1→B5 实施，首版不并行写入、不跨平台扩张。
