# 问题与解决中心方案

日期：2026-11-04。状态：方案与首批历史档案已形成，菜单、查询接口及页面待实现。

## 1. 目标与推荐范围

将体验中发现的问题和开发中遇到的故障，持续记录为可查阅的项目经验。用户以后能按现象搜索，知道原因、如何处理、是否已验证及哪些结论仍不确定。问题修复、历史执行结果和商店受理是不同事实，不能互相替代。

建议第一版新增全局菜单“问题与解决”，放在“商店账号”后、“渠道能力”前。收集与更新主要由 AI 在当前开发会话完成，页面先提供只读知识浏览；使用者不用为每次反馈额外填写一份表单。既有聊天反馈、测试失败、诊断与修复过程都可以成为来源。

已有材料先整理为 `docs/issues/catalog.json`，按问题而非聊天轮次组织。用户在其他尚未提供的会话或外部工具遇到的问题不能凭空获知；后续提供线索后继续补录，不承诺后台自动读取所有 Codex 会话。新菜单上线前档案已可随 Git 保存。

## 2. 页面设计

沿用白色 Ant Design 主题，顶部简洁统计，下面是筛选及分页列表；完整详情使用 Drawer，避免又变成很长的卡片页面。

| 区域       | 设计                                                                               |
| ---------- | ---------------------------------------------------------------------------------- |
| 顶部       | 总问题、待处理、待验证、已解决四项统计；统计受当前筛选影响                         |
| 搜索与筛选 | 搜索标题、现象、原因和解决步骤；分类、渠道、状态；显示匹配数量和“清空筛选”         |
| 列表       | 编号／标题、分类与渠道、状态、更新时间、查看；每页 10 条，不默认展开长正文         |
| 详情头部   | 一句话说明问题、当前状态、根因确认程度、验证依据                                   |
| 详情正文   | 发生现象 → 影响范围 → 原因 → 解决办法 → 验证结果 → 避免再次发生                    |
| 关联证据   | 相关问题、代码提交与项目内验收文档；普通用户默认先看到处理步骤，技术证据放在展开区 |
| 窄屏       | 简化列表列数，保留标题／状态／查看；Drawer 占满宽度，操作可触达                    |
| 加载失败   | 真实显示读取失败并提供重新读取，不能用“暂无问题”掩盖数据损坏                       |

建议地址为 `?view=issues`，筛选、搜索、页码及选中编号保存在 URL；刷新／前后退保持定位。打开详情和切换筛选不会执行商店请求。现有壳层 view 目前是局部状态，实施时仅补齐本菜单需要的导航恢复，避免顺带大规模改路由。

例如搜索“上传超时”，可以同时看到“异常原因丢失（已解决）”和“某次结果不明（待定位）”，详情解释关联，但不把两者合并为一次已解决的商店提交。

## 3. 分类、标签和状态

主分类保持少而稳定；渠道及问题性质作为独立筛选，避免“小米错误”“界面错误”“小米界面错误”多套重复目录。

| 分类标识    | 页面名称     | 典型内容                               |
| ----------- | ------------ | -------------------------------------- |
| experience  | 功能与交互   | 页面布局、命名、操作步骤、结果提示     |
| credentials | 账号与鉴权   | 录入、安全存储、账号维护、平台鉴权     |
| artifacts   | 安装包与检查 | APK／IPA 解析、身份和版本、文件接收    |
| publishing  | 渠道与发布   | 平台查询、限频、上传、审核、上架和回执 |
| engineering | 工程与环境   | 工具、构建、测试、macOS 路径、开发约定 |

问题性质为“缺陷／体验改进／能力需求”，渠道为“公共／华为／小米／OPPO／Apple”等已知标签，可多选。状态为“待定位 → 处理中 → 待验证 → 已解决”，另设“暂缓”。严重程度用于排序，不做全自动猜测。

根因确认程度独立记录为“已确认／疑似／未知”。例如确知异常被吞掉，可以确认该代码缺陷；原始上传是否网络超时，则仍可能未知。临时绕行与永久修复分别说明，不能只写“已优化”。

“已解决”必须有本问题的验证证据：自动测试、浏览器验收、手动核对或明确的用户反馈。仅提交代码、仅全局渠道可用反馈、仅怀疑原因均不能替代对具体历史执行的确认。

## 4. 单条档案

首版使用带 `schemaVersion: 1` 的结构化 JSON，避免再引入 Markdown／HTML 渲染依赖。正文使用纯文本及步骤数组，页面用 Typography、Descriptions、Steps／Timeline、Collapse 组合展示。

| 字段                           | 说明                                                       |
| ------------------------------ | ---------------------------------------------------------- |
| id／title                      | 稳定编号，如 RH-0001；按可理解的现象命名，不用 UUID 当标题 |
| kind／category／channels       | 问题性质、主分类及关联渠道                                 |
| status／severity               | 处理状态与影响程度                                         |
| firstObservedDate／updatedDate | 有证据的日期，不补造过去的精确发生时间                     |
| symptoms                       | 用户看到的现象及触发条件                                   |
| rootCause                      | 确认程度与原因；无法确认时明确写出缺失证据                 |
| solution                       | 已做的修复或建议步骤；尚未实现必须明确标记                 |
| verification                   | 实际验证的方法、结果及仍待验证的范围                       |
| prevention                     | 后续如何避免重复出现                                       |
| evidence                       | 项目内文档、真实提交哈希；不放原始敏感日志                 |
| relatedIssues                  | 同次事件的不同原因、复发问题和关联改进                     |

首版以 `docs/issues/catalog.json` 为唯一事实来源，随项目版本发布；README 只负责说明，不重复维护一份问题状态表。记录变多后可拆成单条文件，保持编号和公开查询合同不变。

## 5. AI 收集规则

1. 用户反馈卡住、错误、结果不符或体验问题时，先查现有档案，有同一根因就追加新的现象和证据；不是每轮聊天建一条。
2. 新问题先记录现象和待定位状态，即使当次不能修复也保留。排查假设标为疑似，不能把后来复现的错误码倒填到旧记录。
3. 开发中的可复用故障、回归失败及环境问题同样记录。短暂的误输入或格式修正可以并入所属问题的排查过程，避免充满没有复用价值的条目。
4. 修复后补齐方案、验证方法、限制和关联提交；未运行的测试不得填写通过。用户确认仅按实际确认的范围记录。
5. 任务结束前检查档案是否已更新，与代码一同本地提交。未来复发继续关联原编号，保留原结论，不静默覆盖历史。
6. 记录仅提炼非敏感事实，不写 Client Secret、Token、测试登录材料、账号正文、真实安装包或执行器绝对路径；截图先确认脱敏，不自动复制用户附件到仓库。

## 6. 实现边界

- `packages/contracts`：定义问题档案、分类和状态的公开合同与严格运行时校验；未知字段和非法链接拒绝读取。
- `apps/api`：仅从启动时确定的仓库／构建资源读取目录，提供只读 `GET /api/issues` 和 `GET /api/issues/:id`；不接受浏览器指定文件路径，不加载 SDK。目录损坏返回真实错误。
- `apps/web/pages/issues`：列表、筛选、搜索和详情，UI 只消费公开合同；本地错误页不会因此产生商店写操作。
- 构建产物：将审核后的问题目录显式复制进发布资源，开发和生产都能读取；不能依赖机器上偶然存在的源码绝对路径。
- 第一版不允许网页直接修改 Git 仓库，不做自动上传日志或后台监听聊天。

API 返回当前安装版本的档案，页面显示知识库更新时间。后续需要页面主动反馈时，再将“本机反馈草稿”存到用户数据目录并与仓库档案关联，使用不同来源和归属，不自动污染公共项目知识。

## 7. 实施顺序与验收

| 步骤             | 内容                                                 | 完成条件                                       |
| ---------------- | ---------------------------------------------------- | ---------------------------------------------- |
| 已执行：盘点     | 回看可用会话、Git 与验收文档，建立首批档案和 AI 约定 | 记录有来源，未知原因不补猜                     |
| 下一步：目录合同 | 严格验证、只读查询、构建资源及异常处理               | 记录、编号、关联和链接校验通过，损坏不降级为空 |
| 页面             | 菜单、分类、搜索、分页和详情恢复                     | 桌面／窄屏、键盘、刷新和历史定位可用           |
| 持续维护         | 每次问题处理更新同一档案                             | 代码、方案、验证与知识同步，本地提交           |

验收包含：重复编号、无效状态、秘密字段混入、非法文档链接、关联缺失、未知／未验证记录的准确展示、搜索及多条件组合、分页重置、详情深链接、读失败与空结果的区别。工程运行既有类型／测试／构建／格式检查，页面做真实浏览器验收。

本方案不将菜单页面标记为已完成，也不把资料归档视为历史商店操作已成功。OPPO 当前已独立完成工程接入并提交，真实验收仍由用户对具体计划触发。
